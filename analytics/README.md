# Call Note private analytics

Two Cloudflare Workers share one D1 database: the public, rate-limited collector and a separate dashboard protected by Cloudflare Access. The dashboard deployment sets `DASHBOARD_ONLY="true"` and rejects every `/v1/*` route with 404 before parsing a body, invoking the rate limiter, or accessing D1. Both expose only minimal `/health` status. Sharing D1 avoids duplicating collected data. Only the collector schedules retention cleanup. The desktop installation sends terms/privacy acceptance independently from optional usage analytics. No transcript, audio, meeting title, names, email, paths, arbitrary error messages, IP address, or user agent is stored in D1. An installation UUID is pseudonymous, not anonymous. Cloudflare necessarily handles request/network metadata; configure account-level logging and retention separately. Worker observability is disabled and application code does not log request bodies or errors.

## Setup

Run `npm ci`, `npm test`, and `npm run check` here. The tests use Miniflare's actual D1 implementation and locally generated RSA keys. `npm run migrate:local` prepares local development storage. The configured database ID belongs to the project account; verify it before any remote command.

Before production activation, approve the legal policy text/version and configure the publisher/contact in the desktop legal notices. The initial protocol policy identifier is `2026-10-15`; this repository's draft is not evidence of legal approval. The desktop must keep ingestion disabled until its legal/configuration gate is enabled.

Create a Cloudflare Access self-hosted application for **only** the dashboard hostname (`call-note-dashboard.s-lyapustin.workers.dev`) with an explicit owner allow policy. Access protection on a workers.dev hostname applies to the whole Worker; do not apply it to the collector because desktop requests must remain public. Configure `ACCESS_TEAM_DOMAIN` in `wrangler.dashboard.jsonc` as the exact team hostname such as `team.cloudflareaccess.com` (no scheme or path) and `ACCESS_AUD` as that application's audience. The dashboard Worker independently verifies the signed Access assertion, exact issuer/audience, expiration, and RS256 algorithm on every private route, including asset requests. Missing Access config denies access. Leave the collector's `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` empty in `wrangler.jsonc` so its dashboard, assets, and aggregate APIs remain inaccessible. `assets.run_worker_first: true` must remain enabled in both configs. Workers previews are disabled. Do not add a public assets domain or bypass route.

After configuration review, run `npm run migrate:remote`, then `npm run deploy` for the collector and `npx wrangler deploy --config wrangler.dashboard.jsonc` for the dashboard. Apply migrations once to their shared database. Set Access variables and enable Cloudflare Access on the dashboard before giving out its URL; until configured, it fails closed. No deployment is performed by the tests. Current configured ingestion hostname: `https://call-note-analytics.s-lyapustin.workers.dev`. Public ingestion has a native `INGEST_LIMITER` binding with 60 requests per minute per hashed connecting IP, shared across consent, events, and deletion routes. The Worker validates JSON and the 16 KiB body limit before invoking the limiter and checks the limiter before any database access. It sends only a SHA-256 pseudonym of the connecting IP to Cloudflare's transient rate-limit counters; no IP or IP hash is written to D1 or application logs. Shared IPs can throttle multiple installations; clients should retry after 60 seconds on HTTP 429. Missing limiter configuration fails closed with 503; health checks remain available. Counters are per Cloudflare location and eventually consistent, so this is an abuse guard, not a strict global quota. Installation credentials prevent cross-installation writes but public registration does not prove a genuine app install. Verify namespace `1001` is not reused by unrelated rate-limit bindings. Deployment must not upgrade the account plan automatically; if the binding is unavailable on the existing plan, stop and report that limitation. See [Cloudflare rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

## API

Requests to ingestion require `Content-Type: application/json`, maximum 16 KiB, and exact allowlisted fields. The installation generates a UUID v4 and 32 random bytes encoded as 64 lowercase hexadecimal characters for `secret`. Store this secret locally with restrictive permissions. Only its SHA-256 hash is stored remotely. Credentials are never in URL parameters, dashboard output, or CSV.

- `POST /v1/consent`: `{installationId,secret,termsVersion:"2026-10-15",privacyVersion:"2026-10-15",analytics:boolean,revision:positiveInteger}`. Registers the installation or authenticates it and applies only a strictly newer revision. Identical retries succeed; conflicting/stale revisions return 409. Response `{ok:true,revision,analytics}`. Acceptance and consent history timestamps are generated by the server.
- `POST /v1/events`: `{installationId,secret,events:[...]}`, 1–20 events. Each event has UUID v4 `id`, `name`, UTC calendar `day` (today or previous 89 days), numeric semver string `version`, and `platform` (`darwin` or `win32`). Names are `app_open`, `call_started`, `call_completed`, `feature_used`, and `error`. `feature_used` requires `feature` (`calendar`, `sample`, `export`, `mcp_setup`). `error` requires `errorCode` (`capture_connection`, `capture_backpressure`, `capture_ended`, `renderer_gone`, `other`). Only `call_completed` may include integer `durationMinutes` from 0 to 1440. All other fields are rejected. Consent is checked again inside each SQL insert to prevent a revocation race. Duplicate event IDs are ignored. Response `{ok:true,accepted:number}`; revoked installations return 403.
- `DELETE /v1/installation`: `{installationId,secret}`. Idempotently deletes the matching installation, consent history, and usage records. The client must stop collection and drain/cancel pending consent requests before deletion, discard its queue, and rotate credentials afterward. A deletion tombstone retains only the SHA-256 installation UUID hash and expiration for 90 days. Registration for that UUID returns 410 during this period, preventing delayed consent requests from recreating deleted records. Tombstone insertion and deletion are transactional, including when the initial registration is still pending. No credential, raw installation UUID, or request metadata is retained in the tombstone.
- `GET /health`: `{ok:true}`; does not disclose database or account state.
- Authenticated `GET /api/stats?days=7|30|90&version=0.2.14&platform=darwin`: aggregates only. Optional version/platform filters apply to usage; installation and consent totals remain global. Daily series includes every UTC day in the selected window, with zeros for days without events. `totals.activeInstallations` counts distinct installations across the whole selected window; daily active counts must not be added to infer weekly or monthly actives. Duration sums represent completed calls only when the client supplies duration.
- Authenticated `GET /api/export.csv` uses the same filters and exports daily usage aggregates with fixed numeric/date columns. It never exports installation IDs or individual consent records.

Usage records expire after 90 UTC calendar days via a daily scheduled job. Consent and terms acceptance records remain until installation deletion. Deletion tombstones expire after 90 days and are removed by the same scheduled job. Turning analytics off blocks future ingestion; it does not erase previously accepted usage. The dashboard's accepted total is the current accepted installation count, not a count of every historical consent revision.

D1 is the restricted raw storage source. Do not share database credentials with dashboard viewers. There is no public raw-event query API, and no MCP server is part of this initial deployment.
