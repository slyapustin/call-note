# Native outgoing noise suppression: source and license audit

Verified 2026-10-14. Research only: no product edits, driver installation, system-audio restart, or vendor contact.

## Recommendation

Use a native microphone/DSP helper, a bounded audio buffer, and a dedicated CoreAudio AudioServerPlugIn input device named Call Note Microphone. Users select that microphone in their meeting app. Keep DSP independent of the Python transcription worker and outside real-time HAL callbacks. A Call Note browser capture constraint alone cannot alter another app's microphone stream.

Use Apple voice processing or WebRTC APM as a prototype baseline that does not introduce a separately redistributed neural-model artifact; Apple Voice Isolation remains user-controlled, and AEC/reference routing and ducking must be tested. RNNoise and DeepFilterNet3 remain measured comparison candidates, not license-cleared shipping choices: modern RNNoise model-file rights are also the subject of an unresolved upstream question (#284, verified independently by the parallel research agent). Audit an exact RNNoise source/model version before choosing it; do not infer modern weight rights from the C library license. Keep DeepFilterNet3 benchmark-only until its pretrained-weight redistribution terms are explicit. libASPL is a reasonable driver foundation with a small, slow-maintained upstream; pin it, own compatibility fixes, and do not equate its README's production-ready statement with broad field validation.

## Exact DeepFilterNet v0.5.6 model identity and rights

- Official [v0.5.6](https://github.com/Rikorose/DeepFilterNet/releases/tag/v0.5.6) release: 2023-08-31, source commit `978576aa8400552a4ce9730838c635aa30db5e61`.
- Local benchmark binary `.build/noise-research/deep-filter` SHA256: `4601e7f4e4c03e59a4c5b5000216ef3add3e808799cfccd95e14e83ea4611081`.
- The binary contains the **byte-identical** official v0.5.6 `models/DeepFilterNet3_onnx.tar.gz` archive at byte offset `11987294`. Archive size `7983136`; SHA256 `c94d91f70911001c946e0fabb4aa9adc37045f45a03b56008cb0c8244cb63616`. Therefore the tested binary's embedded default model is confirmed DFN3, not inferred from marketing or an outdated README.
- [Cargo features](https://github.com/Rikorose/DeepFilterNet/blob/v0.5.6/libDF/Cargo.toml): default includes `default-model`; that feature is explicitly DFN3. [tract.rs](https://github.com/Rikorose/DeepFilterNet/blob/v0.5.6/libDF/src/tract.rs) uses `include_bytes!` for the standard DFN3 archive (or separate `_ll` archive if low-latency feature selected). [CLI](https://github.com/Rikorose/DeepFilterNet/blob/v0.5.6/libDF/src/bin/enhance_wav.rs) chooses `DfParams::default()` when no model argument is given.
- Archive inventory is exactly `tmp/export/enc.onnx`, `erb_dec.onnx`, `df_dec.onnx`, and `config.ini`. **No license, copyright notice, README, model card or training-data manifest is in this model archive.** The repository `models/` directory also has no separate license.
- Config explicitly says `model=deepfilternet3`, sample rate 48000, FFT 960, hop 480, convolution lookahead 2, DF lookahead 2. The CLI's delay compensation removes `(fft_size-hop_size)+lookahead*hop_size`, i.e. 1440 samples/30 ms for this configuration; this is distinct from the paper's 40 ms accounting including frame acquisition. Measure end-to-end delay rather than mix these figures.
- Root [LICENSE](https://github.com/Rikorose/DeepFilterNet/blob/v0.5.6/LICENSE) offers MIT or Apache-2.0. The README wording is specifically all **code**. Root license notices name Hendrik Schroeter (2021). The [author paper](https://arxiv.org/abs/2305.08227) explicitly states the framework and pretrained weights were published under an open-source license, supporting permissive intent but not a dedicated weight redistribution grant.
- Current unresolved upstream questions explicitly ask about commercial bundling of these weights: [#697](https://github.com/Rikorose/DeepFilterNet/issues/697), [#700](https://github.com/Rikorose/DeepFilterNet/issues/700), [#709](https://github.com/Rikorose/DeepFilterNet/issues/709), [#712](https://github.com/Rikorose/DeepFilterNet/issues/712). I fetched every comment: no maintainer clarification was present. In #700 a third-party claim of independently trained weights was corrected to a re-export of the upstream checkpoint. Third-party model cards therefore do not settle this.
- Conclusion: code licensing is clear; exact pretrained-weight redistribution is not explicitly clarified. **Do not report commercial bundling as license-cleared or ship the benchmark CLI/model on that assumption.** Keep the artifact as a research benchmark. No conclusion that redistribution is prohibited is warranted either.

## Other engines and installation implications

- [RNNoise](https://github.com/xiph/rnnoise) is a C library with [BSD-3-Clause](https://github.com/xiph/rnnoise/blob/main/COPYING). Modern separately downloaded model weights have an unresolved licensing question in [issue #284](https://github.com/xiph/rnnoise/issues/284); the code license alone does not settle this. Pin actual code and model, audit model-specific notices (older embedded C weights may differ), retain notices, and benchmark the exact version. Its current delayed-spectrum code means 10 ms processing frames are not a total latency guarantee.
- [Apple voice processing](https://developer.apple.com/videos/play/wwdc2023/10235/) provides NS/AEC/AGC through AVAudioEngine or AUVoiceProcessingIO, but Voice Isolation is user-controlled and other-audio ducking/AEC reference routing need careful testing in a companion app. It does not create a virtual input by itself.
- [WebRTC APM](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/g3doc/audio_processing_module.md) supports standalone NS/AEC/AGC with BSD-style licensing; integration scope is larger than RNNoise. Avoid assuming browser capture processing reaches another app.
- [Krisp SDK licensing](https://sdk-docs.krisp.ai/docs/licensing-information) requires a commercial agreement; [platforms](https://sdk-docs.krisp.ai/docs/supported-platforms) include ARM macOS/Electron. [Privacy documentation](https://sdk-docs.krisp.ai/docs/privacy) says local audio processing but network license verification.
- [Koala README](https://github.com/Picovoice/koala/blob/main/README.md) supports ARM macOS and local processing but requires a secret AccessKey, online license validation, and usage limits. The wrapper repository's Apache license is not a promise of unrestricted engine deployment.
- [BlackHole](https://github.com/ExistentialAudio/BlackHole#developer-guides) explicitly requires GPLv3 compatibility or separate licensing for integration. Do not silently embed/rebrand it under Call Note's existing terms.
- [Apple minimal virtual-device sample](https://developer.apple.com/documentation/coreaudio/creating-an-audio-server-driver-plug-in) is standard C AudioServerPlugIn, installed in `/Library/Audio/Plug-Ins/HAL` and followed by reboot. This is distinct from USB DriverKit. No kernel extension or SIP disabling is needed for this design.
- Use optional signed/notarized installer for the driver, with **Developer ID Installer** identity, distinct from Developer ID Application. Electron's normal app update does not update `/Library` components. Plan uninstall, version checks and rollback. [Apple packaging guidance](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

## Acceptance gates

Use identical clean/noisy paired fixtures with fan, keyboard and transient noises; compare bypass/RNNoise/DFN3 with listening as well as aligned signal metrics. Measure latency, p95/p99 per-frame time and underruns while transcription/diarization are active. Verify cleaned audio from an independent virtual-mic consumer, not just the producer output. Exercise physical mic changes, Bluetooth rate changes, sleep/wake, helper crashes, long sessions, and call-app processing enabled/disabled. Test signed installer, fresh-Mac discovery, upgrade and uninstall. No claim of perfect suppression or removal of other speakers is justified by these libraries alone.

## Practical build validation (2026-10-14)

Cloned the exact libASPL v3.1.2 tag (`47f688ed6bb637ab8b7f4b36864734b2b1f69b6b`) into ignored `.build/noise-research/libASPL`. Used only the already installed Xcode 27.0 (27A266a), AppleClang 21.0.0.21000334 and CMake 4.4.4 on this ARM Mac (sw_vers reports macOS 27.0.1 / 26A434). No global tools added.

- Release static library compiled successfully without source changes.
- Debug library and official test executable compiled with `ENABLE_SANITIZERS=ON` (AddressSanitizer), `BUILD_TESTING=ON`, documentation disabled to avoid requiring Doxygen.
- All **47 official tests in seven suites passed**; ctest 1/1 passed, 0.60 seconds total. No ASan failures appeared.
- Both official example bundles, `SinewaveDevice.driver` (input) and `NetcatDevice.driver` (output), compiled as arm64 Mach-O bundles. CODESIGN_ID explicitly empty. Their build staged headers/library only into nested build-directory prefixes; no system install occurred.
- Non-fatal warnings: newer CMake CMP0175 handling of custom-command declarations, and C++ designated-initializer order. These warrant cleanup when vendoring, but did not block the build.
- Logs are `libaspl-debug-build.log`, `libaspl-tests.log`, `libaspl-examples-configure.log`, `libaspl-examples-build.log`, and release-build logs beside this report.
- No example was copied to `/Library`, loaded by HAL, signed/notarized, or used as a microphone. Unit/build success is **not** live audio, installation or meeting-app validation.

A standalone `libaspl-period-probe.cpp` reproduced the exact PR #13 observation without starting an audio device: default rate and period both begin at 44100; after allowing 44100/48000 and setting rate to 48000, both operations return success while period stays 44100 frames. The source documents the period in **frames**, and `GetZeroTimeStampImpl()` recalculates host ticks per frame after rate changes. Therefore the unchanged frame period alone does **not** demonstrate incorrect clock speed, drift, or audible glitches; it becomes a 0.91875-second period instead of one second. The PR's claimed failure needs real timestamp/route testing before adopting its patch. A first implementation with a fixed 48 kHz device and explicit period avoids relying on automatic period-follow-rate behavior. More generally, pause/restart, timeline continuity and hardware-rate conversion must still be tested.
